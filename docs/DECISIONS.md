## ADR-001: Монорепозиторий, портируемость через манифест
**Дата**: 2026-08-24

**Контекст**: Проект должен целиком жить в `/projects/server`, синхронизироваться с GitHub и легко переезжать на другой VPS. Миры и jar-файлы — большие/бинарные, git от них распухает.

**Решение**: Один репозиторий: конфиги, исходники плагинов, инфраскрипты, документация, позже сайт. Бинарники НЕ в git — все jar-ы пинятся в `infra/manifest.json` (версия + URL + sha256) и скачиваются `infra/download.sh`. Данные (миры, БД) — не в git, переносятся бэкап-скриптом (tar миров + pg_dump).

**Последствия**: Перенос сервера = `git clone` + `infra/download.sh` + восстановление бэкапа данных + `infra/secrets/`. Обновление плагина = правка манифеста (история версий видна в git).

## ADR-002: Топология — Velocity proxy + Paper backends
**Дата**: 2026-08-24

**Контекст**: Целевой формат — мультирежимный сервер (лобби, выживание, дальше креатив/мини-игры) с ростом до большого онлайна. Альтернатива — один Paper-сервер с мирами через Multiverse.

**Решение**: Сеть: Velocity proxy (единственная точка входа) + отдельные Paper-серверы на режим: `lobby`, `survival` (дальше — по мере роста). Backend-серверы слушают только 127.0.0.1, наружу торчит только proxy. Связь через modern forwarding с секретом.

**Последствия**: Режимы изолированы (лаги/крэш одного не кладут всё), масштабирование добавлением backend-серверов, при переезде на мощный VPS топология не меняется. Цена — больше JVM (на 8 GB RAM держим одновременно только одну сеть: dev ИЛИ prod под нагрузкой).

## ADR-003: offline-mode + плагин авторизации (регистрация), premium auto-login
**Дата**: 2026-08-24

**Контекст**: Нужна система регистрации/авторизации (запрос владельца). Значительная часть RU-аудитории играет без лицензии. Bedrock-игроки в принципе не имеют Java-аккаунтов.

**Решение**: Proxy в `online-mode=false`. Авторизация плагином: пароль для нелицензионных игроков, автоматический вход для лицензионных (premium auto-login), Bedrock-игроки через Floodgate проходят без регистрации (Xbox-аутентификация). Конкретный плагин — по итогам ресёрча (см. ADR-007).

**Последствия**: Максимальный охват аудитории. Риски offline-режима (подмена ников, вход в чужие аккаунты) закрываются: авторизация обязательна до любых действий, backend-серверы недоступны напрямую, modern forwarding с секретом, сессии с привязкой к IP.

## ADR-004: PostgreSQL 16 — единая БД проекта
**Дата**: 2026-08-24

**Контекст**: Нужно надёжное хранилище под авторизацию, права (LuckPerms), экономику, позже сайт. Владелец предпочитает PostgreSQL. Альтернативы: SQLite/файлы (не тянут рост), MySQL/MariaDB (у части MC-плагинов поддержка шире).

**Решение**: PostgreSQL 16 локально (127.0.0.1:5432), базы `magnaqore_dev` и `magnaqore_prod`, пользователь `magnaqore` (креды в `infra/secrets/db.env`). Плагины выбираем с учётом поддержки Postgres; для плагинов только с MySQL-поддержкой допускается их встроенное хранилище (H2/SQLite) как исключение, если данные некритичные.

**Последствия**: Одна СУБД для сервера и сайта, простой бэкап (pg_dump), высокая нагрузостойкость. Немного сужается выбор плагинов.

## ADR-005: Кроссплей Java + Bedrock (Geyser + Floodgate)
**Дата**: 2026-08-24

**Контекст**: Владелец хочет мультиплатформенность (ПК + телефоны), но не ценой урезания функционала.

**Решение**: Делаем. GeyserMC + Floodgate на уровне Velocity. Функционал Java-игроков не режется вообще — сервер остаётся полноценным Java-сервером с плагинами. Ограничения существуют только для самих Bedrock-игроков (отдельные мелочи интерфейса/механик транслируются неидеально) — это приемлемо.

**Последствия**: Дополнительный UDP-порт (19132 prod / 19133 dev), Bedrock-игроки получают префикс в нике (настройка Floodgate), аудитория заметно шире.

## ADR-006: dev в tmux, prod в systemd
**Дата**: 2026-08-24

**Контекст**: Нужны два контура — dev (частые перезапуски, живая консоль) и prod (автозапуск, устойчивость).

**Решение**: dev-сеть управляется `infra/dev.sh` (tmux-сессии `mq-dev-*`, консоль под рукой). prod — systemd-юниты (`infra/systemd/`, автозапуск при ребуте, Restart=on-failure) — оформим на этапе публичного запуска.

**Последствия**: Быстрая итерация на dev; prod переживает ребуты VPS без ручного вмешательства.
